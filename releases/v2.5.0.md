# sys-buddy v2.5.0 — 2026-08-05

Minor release. **The desktop app can finally put more than one person on a role.** No
schema change, no migration, and nothing touched in the broker, the auth path, the stream
or the database — the entire change is `gui_app.html`.

Which is the point worth stating plainly: the broker has accepted "two frontend
developers" since **v2.0.0**. `normalise_cast` numbers a repeated role into
`@frontend-1` / `@frontend-2`, invites are minted per SEAT, and party lists take seats
rather than role types. All of that shipped, was tested, and was reachable only from the
CLI. The surface almost every host actually uses could not express it.

## Added

### A role is a count, not a checkbox

The app's cast was `{ backend: true }` — a boolean, with no notion of *how many*. A
two-frontend task was unreachable from the app no matter what the broker underneath was
willing to do.

The cast is a **count** now. Each role chip gains a `+`, shown only while the role is on
and still under its cap, so it never renders as a dead control. The count appears beside
the role as `×N` **only once N exceeds one**, which is what keeps the common case quiet:
a one-of-each cast renders exactly as it always did.

| | |
|---|---|
| cap per role | **6** |
| cap for `owner` | **1** — one client, by definition |
| one-of-each output | byte-identical to before: `['backend','frontend']` |

`castRoles()` expands the counts into the repeated array that `create_task` already read,
so the app is now speaking a language the broker has understood for five releases rather
than being taught a new one.

### "A contract needs two agents" counts SEATS, not role types

Deliberate, and it is the reason a frontend-only session is now legitimate: two frontends
are two agents who can hold a contract with each other. The old check counted distinct
role **types**, so "just FEs" was refused as if nobody were there to sign — a rule that
made sense when a role meant a person and stopped making sense in v2.0.0.

`castTypes()` still exists for the things that genuinely care about distinct types; the
minimum now asks `castRoles()`.

## Migration

* **None.** No schema change, no new table, no tool renamed or removed, no payload key
  changed. A one-of-each cast submits exactly the same array it submitted in 2.4.0.
* **Restart any long-running broker** to pick up the new `gui_app.html`. A process started
  before this release keeps serving its old copy.

## Tests

**1432 passing**, up from 1428.

Verified in a browser by stubbing the bridge: a cast of **2 backend + 3 frontend**
produced exactly the five numbered seats — `@backend-1`, `@backend-2`, `@frontend-1`,
`@frontend-2`, `@frontend-3` — and one-of-each submitted the unchanged two-element array,
which is the case that would have broken silently for every existing user.
