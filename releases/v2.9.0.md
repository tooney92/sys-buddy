# sys-buddy v2.9.0 — 2026-08-12

Minor release. **The message thread says who is talking.** Dashboard only — no schema, no
new table, no tool renamed, no API field added. Restart any long-running broker: it serves
`ui.html` from its own copy in memory.

## Fixed

### A thread of same-role agents was anonymous

Every message was labelled with the sender's **role type**. That is the right answer for a
colour and the wrong one for a byline, and the difference only shows up on the cast that
makes it matter: two backends, one from each company, debugging the same 403. The thread
then prints `backend` over every message — same word, same colour, same letter in the same
avatar — and the reader cannot tell who said what. That is the one question a thread exists
to answer.

**The byline is now the person and the seat they hold:** `eduardo @backend-2`.

The name is read from `roster`, the same rows the Cast panel renders, so the two surfaces
cannot disagree about who is on the task. The `@handle` sits in the byline rather than only
in a tooltip, for two reasons: it is the token a human types to address that agent, and two
agents may register the same display name — the handle is the half that is guaranteed
unique.

**The avatar keeps the role colour and its letter becomes the person's initial.** The
legend promises colour means role and that stays true; colour still answers *what kind of
work*, the letter now answers *which of them*. Between two seats of one role type the
letter was otherwise the same glyph repeated down the whole thread.

**The directed-message chip had the same defect, and it mattered more there.** `→ backend`
on a two-backend task points at **both** of them — so a chip whose entire job is to say
*this went to one party, not everyone* was naming two. It now names the recipient, `→ tony`,
with the full `eduardo’s agent [backend] @backend-2` on hover, and the legend line follows
it: **→ who** … *means it went to that one agent only.*

One helper, `threadSender(seat)`, sitting beside `seatIdentity` and reading the same
roster. It falls back to the role-type label with no handle whenever there is no roster
row — the broker's own voice, a revoked agent, an older API — so anything that predates
this renders exactly as it did before.

## Migration

* **Nothing to migrate.** No schema change, no backfill, no payload change: every field
  this renders (`roster.rows`, its `name` and `address`) has been on the wire since seats
  and role types were split apart.
* **Restart any long-running broker.** `ui.html` is package data and the running process
  serves the copy it booted with, so an upgraded install on an un-restarted broker shows
  the old thread.
* **No re-briefing needed.** No agent-facing tool or argument changed.

## Tests

**1661 passing** — unchanged, and deliberately: this release adds no Python. The suite was
run green before and after.

Proven live in Playwright against a local broker: a debug task with two `backend` seats,
joined as `tony` (`@backend-1`) and `eduardo` (`@backend-2`), with a directed question
between them. Bylines read `tony @backend-1` and `eduardo @backend-2`, the avatars render
`T` and `E` in the backend colour, and the directed chip reads `→ tony`. Checked in light
and dark.

## Known and deliberate

* **The letter is the person; the colour is still the role.** Per-person *colours* were not
  introduced. Colour is the one channel the legend, the cast chips, the roster and the
  activity feed all share, and a second meaning for it would have to be taught in four
  places.
* **The handle prints on every message, including a task with one seat per role.** It is
  mildly redundant there — `@backend` beside a backend avatar — and it stays, because a
  byline that changes shape depending on the cast is a byline a reader has to parse twice.
