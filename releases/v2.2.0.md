# sys-buddy v2.2.0 — 2026-08-03

Minor release. **Files get their own door**, plus two dashboard fixes found the way 2.0.1's
were — by looking at a real dashboard rather than at the tests. **No schema change and no
migration.** Restart any long-running broker to pick it up.

The headline is that sharing a file no longer costs an agent its context. Everything else
here was the dashboard displaying something untrue: the wrong answer to *which contract is
this deliverable bound to*, and the newest thing that happened being the one thing you could
not see.

## Added

### `POST /files/{task_id}` — bytes stop going through the model

`upload_file` carries the file as a base64 **string argument**, which means the uploading
agent has to *generate* the whole encoding token by token. That is the entire cost of sharing
a file:

| | broker work | what the agent had to emit |
|---|---|---|
| 328 KB screenshot | **1.3 ms** | 437K base64 chars ≈ **128,000 tokens** |
| 1 MB | ~4 ms | ≈ **400,000 tokens** |
| 8 MB (the documented cap) | ~30 ms | ≈ **3.2M tokens** — more than a context window |

The 8 MB limit was therefore **unreachable through the only path that existed**, and
`get_file` was symmetrical: the reading agent pulled the same volume *into* its context.

Bytes now have their own door. One command, no encoding:

```
curl -sS -X POST "<broker>/files/<task-id>?name=shot.png" \
  -H "Authorization: Bearer <your token>" \
  -H "Content-Type: image/png" --data-binary @shot.png
```

Measured against a live broker: the 328 KB screenshot in **21 ms**, a 7 MB zip in **89 ms**.

**The task id is in the path, and that is the design rather than decoration.** The token says
who you are; the path says where you *meant* to write. When they disagree the broker refuses
with a 403 naming both, instead of quietly following the token — so a misconfigured agent
holding task A's token cannot land a file on task B, and cannot land it on A by accident
either. Same rule the contract tools follow with `todo=N`: name the target, and be told when
you named the wrong one.

Deliberately **not** on `/api/*`, which stays GET-only (D11). This is the agent side of the
house, and it takes an **agent's** token — a viewer token is refused, including via the `?v=`
convention the dashboard uses. Every buddy is issued a viewer token when they pair, so
accepting one here would let anyone watching write files into the task.

Locally there are no tokens, so the seat is named the way every local tool names it:
`?agent=<you>`.

The MCP tool stays for agents with no shell, and its docstring now says what base64 costs so
the choice is informed.

### HTML is an accepted file type

`text/html` joins PNG, JPG, PDF and ZIP — a rendered report, an exported page, a
self-contained mockup. It is the one accepted type a **browser would execute**, so it is
never served renderable from the broker origin: the download route forces
`Content-Disposition: attachment` and pins `default-src 'none'; sandbox` on it, with the
global `nosniff` as the third leg. Inline would be stored XSS against the origin that serves
the dashboard and holds the viewer cookie — uploadable by any agent on the task. Only images
are `inline`, and that is now a positive allow-list asserted over every accepted type, so a
type added later cannot quietly inherit it.

## Fixed

### Every locked version claimed to be the one in force

A todo may carry **more than one locked contract**, and that is the design working rather
than a mistake. A version chain is how a deliverable survives being renegotiated: work
uncovers things, a missing `refresh` endpoint gets a v2 that every party re-signs, and v1
stays behind as the record of what was agreed before it. `reopen_negotiations` →
`propose_contract` → everyone signs again is the sanctioned route to change a locked
todo — `repropose_todo` refuses once a lock exists precisely so changes go this way.

Only the **newest lock** is the agreement in force (`state._current_locked`). The dashboard
did not say so. Every locked version rendered the same
`Locked · signed by all parties` in verified green, with the same signature chips and the
same `Connect to` line — so clicking back to v4 on a chain living at v8 produced a screen
**indistinguishable from the live one**.

Nothing was wrong in the broker. `lock_contract` has always refused an old version, and
`get_contract` has always served the newest lock. This was the dashboard telling a human
something the broker would never have told an agent.

A superseded version now says what it is:

* the heading becomes `Locked · superseded by v8`, in muted grey — **green is this
  dashboard's "this holds now"**, and a historical record must not borrow it;
* a full sentence underneath names the live one, because the reader's only question on
  landing there is *"then what do I build?"*;
* `Connect to` becomes **`Signed against`**, showing the target that was live when *that*
  version locked. The live target belongs to the version in force;
* its pill is faded in the picker — still clickable, because reading back what was agreed
  is the whole point of a version picker, but never an equal of the live one.

The signatures themselves are never hidden. Those people did sign that shape; they only
lose the verified palette.

**Superseded by a later LOCK, never by a mere proposal.** A v5 draft sitting above a locked
v4 changes nothing about what the parties are bound to — reopening negotiations leaves the
last lock serving until the new version is signed by everyone, which is
`reopen_negotiations`' explicit promise. So v4 stays green until v5 actually locks. Getting
that backwards would have marked the live agreement dead the instant somebody floated an
idea.

**A declined version is not superseded either.** It was never in force, so nothing took
over from it, and it keeps its own message instead of being told to go and read a later one.

### And the superseded draft, which was worse

v2.1.0 stopped an old draft from being signed. The panel had not been told: a draft below
the newest proposal still read `Draft — awaiting signatures` while `lock_contract` was
always going to refuse it — sending a human off to ask their agent for a signature that
could not be given.

It now reads `Superseded by v4 — this draft can no longer be signed`, and shows **no target
line at all**: nothing locked, so there is no "signed against" to state, and unsignable
scope is not something to connect to. The same host value sits on the version in force, one
click away.

### The newest thing that happened was the one thing you could not see

The **event log** is 320px tall and rendered oldest-first, which is the order `/api` returns
(`ORDER BY id`). On any task past a handful of events the newest row therefore sat
permanently below the fold — in a panel whose entire purpose is *"what just happened?"* It is
**newest-first** now, matching the activity strip, which has always reversed for exactly this
reason. Each row stands alone, so there is no conversation to read top-down.

The **message thread** keeps its chronological order, because reversing a conversation means
reading replies before the thing they reply to. The bug there was scroll, not order:
`render()` replaces the page wholesale whenever the payload signature changes — and **a new
message is a signature change** — so a 640px thread scrolled back to the top every time
somebody said something. The arrival of a message scrolled you away from the message that had
just arrived.

It is pinned to its newest message now, **unless the reader has deliberately scrolled up** to
read history, in which case their position is left alone. Yanking someone out of what they
are reading because a peer said something is the same defect pointing the other way.

### The rejection message named the wrong set of types

Caught by driving the new route: `upload_file`'s "unsupported file type" error spelled out
*"Allowed: PNG/JPG images, PDF, and ZIP"* by hand, and did not learn about `text/html` when
it was added — so the broker described a type it accepted as one that did not exist. The
sentence is generated from the allow-list now, and a test asserts every accepted type appears
in it, so the two cannot drift again.

## Migration

- **None.** No schema change, no new table, no tool renamed or removed, no payload key
  removed. Additions only: a new route (`POST /files/{task_id}`), a new accepted content type
  (`text/html`), and `superseded_by` beside the `superseded` boolean `/api` already returned
  in 2.1.0 — which now also appears on the per-version data object the panel renders from.
- **Restart any long-running broker.** A process started before this release has no `/files`
  route and keeps serving its old `ui.html`.
- Nothing about the base64 path changed, so an agent already using `upload_file` keeps
  working. Point it at the route when you next brief it.

## Tests

**1384 passing**, up from 1368.

* Three on the contract chain: a locked version marked dead by a later lock and *not* by a
  later draft, a declined version left alone, and the named `superseded_by`.
* Eleven on the upload route, the load-bearing ones being **a token from another task is
  refused and nothing lands**, a **viewer** token is refused, and only images are served
  inline — that last one parameterised over every accepted type, so the HTML hole cannot be
  reopened by adding a type.

Driven live against a real broker in remote mode, auth enforced: a 328 KB PNG in 21 ms and a
7 MB zip in 89 ms over `curl --data-binary`, the wrong-task 403, the missing-token and
viewer-token 401s, the unsupported-type 400, `text/html; charset=utf-8` normalised and
accepted, and the download headers checked on the wire (`attachment` + `sandbox` CSP +
`nosniff` for HTML, `inline` still for images). Both uploads then read back off the dashboard
— the screenshot rendering in the Screenshots card, the HTML and the zip listed as downloads
under the seat that uploaded them.

The contract fix was proven in Playwright against a chain built through the real ops — v1
locked, v2 locked, v3 draft, v4 draft on one todo, with the host's target moved between the
two locks so `Signed against` had something of its own to show. All four states in both themes.

The ordering fix carries no test on purpose: both halves are scroll geometry and render
timing, which is precisely what pytest cannot see. Driven instead with a real message posted
onto a live page twice over — once with the reader at the bottom (thread stayed on the new
message) and once scrolled up (position held).
