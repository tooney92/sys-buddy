# sys-buddy v2.6.0 — 2026-08-06

Minor release. **A debug task carries ISSUES, and both parties agree each fix.** One new
table (`todo_fixes`), created on boot — no data migration, nothing to run by hand.
Restart any long-running broker to pick it up.

## Added

### A debug session is no longer one problem

A debug task used to be a single problem you fixed and closed with
`report_status("resolved")`. It now carries several **issues**, and the shape is worth
stating precisely: **an issue is a todo with the contract half removed.** There is no
*how* to agree on a bug — only whether it is real, and whether it is fixed.

```
issue <title>   anyone raises one; raising IS the raiser's own acceptance   → pending
yes #N          every OTHER named party accepts it is real                  → accepted
fixed #N        each party says independently that their side is fixed      → still accepted
fixed #N        the last party lands it                                     → resolved
```

The implementation is the point: it is the **same `todos` table**. Numbering, party
lists, accept / decline / repropose / drop, the stuck flag and the rollup are code that
already existed and was already tested. `propose_issue` is `propose_todo`'s own
implementation under the other name, and each refuses on the other's mode with a redirect
that names the right one. Which of the two a row *is* comes from `tasks.mode` every time,
never from a parameter — so there is no way to end up with an issue on a contract task
because a caller passed the wrong flag.

### `fixed #N` requires EVERY party, not the first one to notice

The same all-must-agree rule `lock_contract` applies to signatures, over the same "all".
Your `fixed` records **your side only**; while any party has not reported it, the issue
stays `accepted`. That is a normal state, not an error — and it is the whole point:
nothing here closes on one agent's say-so, and you are meant to check your own side
rather than take your peer's word for it.

Records live in the new `todo_fixes` table, **version-scoped** exactly like the
acceptances in `todo_decisions`: a repropose issues a new version, and fixes recorded
against the old one do not carry over.

### The task resolves by rollup, and does not latch

When every live issue is resolved, the **task** resolves by itself — you never report
that. It also goes backwards: resolved-because-counted reopens the moment a new issue
appears, with no human needed. Resolved-because-a-person-said-so stays terminal, and the
provenance is the task-level `resolved` event.

`report_status("resolved")` still closes a debug session that carries **no** issues — the
old single-problem shape is intact. Once a session has any, the bare form is refused,
because "resolved" says nothing until you name which one.

### CI now fails when `uv.lock` disagrees with the project

`.github/scripts/check_lockfile.py`, wired into CI. release-please bumps
`pyproject.toml` and not the lockfile, so main has repeatedly shipped with the two
disagreeing and every `uv run` dirtying the working tree — v2.4.0's note records it at
2.2.0/2.3.0, and it happened again at 2.5.1.

It fired for the first time on the release that shipped it, catching exactly that drift
on this release PR. **Known consequence:** every future release PR will fail this check
until its `uv.lock` is updated, because release-please does not touch the lockfile. Until
release-please is configured to bump it, that is a manual commit on the release branch.

## Migration

* **One new table, `todo_fixes`,** created on boot like every other. No backfill, no
  data migration, nothing to run by hand.
* **No tool renamed or removed.** `report_status("resolved")` keeps working on a debug
  session with no issues.
* **Restart any long-running broker.** A process started before this release has no
  `propose_issue` and keeps serving its old `ui.html`.
* **Re-brief your debug-task agents** — the briefing now teaches the issue lifecycle, and
  an agent briefed before the restart holds the old text.

## Tests

**1476 passing**, up from 1434 — `tests/test_issues.py` is 601 new lines on its own.

The load-bearing ones are about the rule that nothing closes on one agent's word: a
partial `fixed` leaving the issue `accepted` rather than erroring, the last party landing
it, fixes not carrying across a repropose, and the task rollup reopening when a new issue
arrives on a resolved task.

Merged against a main that had moved two releases underneath it, so the branch was rebased
and the full suite re-run — both sides' tests green together, which is the thing a stale
green CI run cannot tell you. The Commands panel was driven in a browser on a real debug
task afterwards: Messaging · **Issues** · Status · Files · Meta, with `issue`/`yes #N`
under Issues and `fixed #N` under Status.
