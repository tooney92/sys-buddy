# sys-buddy v2.11.0 — 2026-08-15

Minor release. **Concierge is in the GUI now: a guest is a role you pick, not a name you
type.** No schema change. Restart any long-running broker — it serves `gui_app.html`,
`join.html` and `ui.html` from its own copy in memory.

## Added

### Pick "guest" like any other role — and the guest names themselves

v2.10.0 shipped the Guest seat, but only through the CLI (`sys-buddy task add-guest`,
where the **host** typed the guest's name). That is half a feature: every other seat is
chosen in the role picker and self-named by the person who joins. A guest should work the
same way, and now does.

The host picks **`guest`** in the role picker — one or more, alongside backend / frontend /
mobile / designer — and sends the invite link exactly as they would for a buddy. The
**guest** opens the link, types their **own** name on the join page, and lands on their
board. The host never types anyone's name.

### The guest's invite redeems to a board, not an agent

The seam is one branch in the pairing flow. A normal invite mints an agent token for an AI
to configure; a **guest invite mints a viewer LINK** instead — a tokenless, auto-ready seat
plus a viewer bound to it (the dashboard message box). So the *same self-naming invite
flow* every buddy uses produces, for a guest, the one thing a non-technical person needs:
a link to their board. No agent token is ever created for a guest, because there is no
agent.

### The join page knows a guest when it sees one

Open a guest invite and the join page drops the whole agent-setup path — no "connect your
agent", no briefing prompt, no client config. It shows a name field and a single button,
**"Join & open my board"**, and ends on *"You're in — open your board."* The page reads the
seat's role type off the preview it already fetches, so the guest never sees a step that
does not apply to them.

### Guest in the picker: never "you", never a builder

Two rules keep the picker honest:

- **A guest is never "you".** The host runs the broker and is a developer; a guest has no
  agent. So the guest chip has no "you" toggle at all, rather than one that would be refused.
- **A guest does not count toward the contract minimum.** A contract needs two *builders* —
  two agents that can produce and sign. `backend + guest` is one builder, so the picker
  still asks for one more. `guest` is offered on **every** mode (unlike `owner`, which is
  engagement-only): you can want a client watching a plain contract task, not just an
  engagement.

## Fixed

### A guest can no longer stall an engagement lock

`builder_handles` — the list of seats that must sign a deliverable list — now excludes the
guest, exactly as it already excludes the owner. A guest cannot sign anything, so counting
one would leave a deliverable list waiting forever on a signature that can never come. It
mattered less for the owner (who authored the list); for a guest it would have been a hard
deadlock the moment a guest was on an engagement.

## Migration

* **No schema change.** A guest seat is an ordinary seat in the cast; its invite is minted
  and redeemed through the existing pairing machinery, with one branch for the tokenless
  outcome.
* **No agent-facing tool changed**, and buddies need **no re-briefing** — a guest's message
  arrives in the thread like any other.
* **Restart any long-running broker.** `gui_app.html`, `join.html` and `ui.html` are package
  data; a running process serves the copies it booted with.

## Tests

**1673 passing**, up from 1671.

New coverage: redeeming a guest invite returns a **view link, not an agent token**, and the
link resolves to a real, writable guest seat; `builder_handles` excludes the guest on an
engagement cast.

Proven live in a browser against a local broker: a task with a `@guest` seat, its invite
opened cold, "Ada" typed on the join page, **"Join & open my board"** clicked — landing on
*"You're in, Ada"* and then on the board as **Ada @guest**, where her message posted. The
picker shows the `guest` chip with no "you" toggle. Checked end to end.

## Known and deliberate

* **Concierge is a role, not a fourth session type.** The modes (Contract / Debug /
  Engagement) describe how the *work* runs; a guest is a *participant* who can sit inside any
  of them. A "Concierge mode" radio would force a false choice — this is a Contract task
  *with a guest*, not a different kind of task.
* **Host-vouches still.** A guest talks to the host's plain-speaking agent — right for a
  trusted collaborator, not an arm's-length client who needs their own independent agent.
* **A guest invite's desktop/CLI (`sb1_`) alt link is not for a guest** — she uses the
  browser link. The CLI join path would redeem it, but a guest has no agent to configure, so
  the browser link is the one to send.
