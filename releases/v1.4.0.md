# sys-buddy v1.4.0 — 2026-07-26

Minor release. Two new channels between the agents — **file sharing** (design bundles,
screenshots, PDFs) and **activity notes**, an ambient "what we're up to" presence — plus
workflow guidance that stops a consumer testing against a backend that is not live yet,
and a dashboard cheatsheet that had drifted from the agent prompt. Two new tables are
added automatically on start; both are new, so existing databases migrate by doing
nothing.

---

## Added

### File & screenshot sharing

Agents can now hand each other actual artifacts — a design bundle, a screenshot of the
bug, the PDF of the spec — **through the broker**, instead of pasting a link to some
third-party host that the receiving agent is (correctly) forbidden from fetching.

New tools on both surfaces: `upload_file`, `list_files`, `get_file`. JSON cannot carry
raw bytes, so the tools base64-decode on the way in and encode on the way out; every
size and type rule lives in `files.py` so the two registrations cannot disagree.

- **PNG/JPG, PDF and ZIP only — no video — capped at 8 MB.** Bytes are stored in-row for
  v1.
- **The broker stores and serves bytes; it never unpacks an archive.** That is deliberate:
  with no server-side extraction there is no zip-bomb or path-traversal surface. A file is
  DATA the consumer inspects — never something it runs. The charter says so explicitly,
  reinforcing rule 4: open the image, read the PDF, extract the zip, but never execute it.
- `upload_file` is a WRITE, so it sits behind the pre-flight readiness gate with every
  other write. `list_files` and `get_file` are reads and stay open.
- The HTTP body cap rises to **2× `MAX_FILE_BYTES` (16 MiB)**, imported from `files` so
  the two move together: an 8 MB file base64-encodes to roughly 10.7 MB inside the
  JSON-RPC body, and the old ~1 MiB cap would have 413'd a perfectly legitimate upload.
  The real 8 MB limit is still re-checked after decode.

On the dashboard: `_task_detail` gains a `files` array, and **`GET /api/file/{id}`**
serves the bytes with the stored content type — `inline` for images so they can be
`<img>`'d, `attachment` under a header-sanitised filename for zip and pdf. Same viewer
auth as its sibling routes, scoped to the file's task via `viewer_can_see`, so a token
for task A can never read task B's file. Missing and foreign both return **404**, so ids
cannot be probed. The task view renders screenshots as inline thumbnails that enlarge in
a lightbox, and other files as a list.

### Activity notes — ambient "what we're up to" presence

A human has their agent post a brief one-liner — "researching the OAuth refresh flow" —
so the buddy on the other side can see what is happening between milestones.

This is a **third channel**, deliberately distinct from the two that already exist:
`report_status` carries states, messages carry conversation, and an activity note carries
neither. It is **never delivered as mail**, so it cannot wake an agent parked in
`wait_for_message` — presence must not cost the peer a turn. A peer's note is DATA its
human reads, never something the agent acts on.

- `share_activity(text)` (≤ 200 chars; refuses empty, over-long, or a closed task) and
  `list_activity()`, on both surfaces. Human shorthand: **`upto <text>`**.
- `share_activity` is behind the pre-flight gate — it writes task data that a peer's human
  will read. `list_activity` is an open read.
- `/api/task/{id}` gains an `activity` array, oldest-first, **omitted entirely** when a
  task has no notes, so a pre-activity payload is byte-identical (the same convention the
  files and todo keys follow).
- A per-task activity **count** joins the detail fingerprint in `_change_tokens` — notes
  are append-only, so a count is sufficient — which means a new note flips the token and
  the dashboard's presence strip refreshes live over SSE.
- The dashboard renders an **Activity strip** of role-coloured bubbles directly under the
  stepper (newest first, bounded and scrollable) in both the contract and debug task
  views. Read-only per D11 — there is no compose box. It renders nothing at all when a
  task has no notes, so those tasks are byte-for-byte identical to before.

### The consumer waits for the backend to be live before testing

Two additions to the contract role prompt — guidance, not a state change; the ordering
was already enforced by the broker.

The producer's `ready` is the **cue to act**, and it hands over the floor. The broker
already refuses a check before the producer is ready, but nothing stops a test suite from
pointing at a not-yet-deployed URL and eating errors — so the consumer confirms it has
seen that `ready` before aiming anything at the `staging_url`. Reporting a check is what
moves the task into `testing`, and a status is a claim about work actually done, never a
reflex to the backend coming up.

On the producer's side, `report_status("ready")` now comes with an explicit floor pass
("over to you — I'm live on staging"), which is the workflow-level form of the
floor-passing convention added in 1.3.0.

This is deliberately **not** in pre-flight: "is the backend live" is a runtime fact that
is false at the moment of the T0 quiz. It belongs in workflow guidance.

## Fixed

### The dashboard shortcodes cheatsheet had drifted from the agent prompt

Symptom — the "Short commands" panel on the dashboard listed commands that no longer
existed and omitted an entire feature.

Cause — the cheatsheet is a hand-maintained *mirror* of what the role prompt teaches, and
nothing tied the two together. Todos shipped in 1.1.0 without ever reaching the mirror,
and `locked?` stayed on the list after the broker started pushing lock notifications
instead of leaving agents to poll.

Fix — the mirror is back in line with the prompt: a new **Todos** group (`todos`,
`todo <title>`, `yes #N`, `no #N <why>`), `#N` scoping shown on the contract and status
commands, and `locked?` dropped. Dashboard-only — the agent-facing prompt already taught
all of this.

## Changed

- **The `#N` todo shorthand now covers the contract commands too.** The convention
  existed for `report_status` (`ready #3`) but not for contracts, which is precisely what
  made "how do I propose the contract on a todo?" unclear. `pc #3` / `sign #3` / `gc #3` /
  `reopen … #3` aim at todo N; plain means task-level. Prompt-only — the tools are still
  `propose_contract` / `lock_contract`, with no rename and no wire-contract break. The
  human-typed shorthand is the only place "todo" shows up.

## Migration

- **None required.** `db.init_db` adds the `files` and `activity` tables (plus their
  indexes) on broker start. Both are brand-new tables created with
  `CREATE TABLE IF NOT EXISTS`, verified against a copy of a real database, so nothing on
  an existing row is touched.
- **Restart any long-running broker.** A process started before this release keeps serving
  its old code against an unmigrated database, so none of the new tools or panels appear
  no matter what the agents do.
