# sys-buddy v1.2.0 — 2026-07-25

Minor release. One agent-invisible but operationally important feature — **version
awareness** — plus the packaging and release plumbing: a Docker image, and an automated
conventional-commit release pipeline that publishes to PyPI and ghcr. No changes to the
tool surface, no schema changes, no migration.

---

## Added

### Version awareness — the broker can be running older code than you installed

A broker process started before an upgrade keeps serving the module it booted with.
Nothing surfaced that. It is exactly the drift that hid the 1.1.0 startup crash: the
fix was installed, the running process had never reloaded it, and the symptom looked
like a code bug.

- **`GET /api/version`** reports the version *this process booted with*. It is
  unauthenticated — a version string leaks nothing, and the callers that need it (the
  desktop app, a dashboard with no viewer token yet) often hold no credential. GET-only
  like every route on that surface, per decision D11. It is an endpoint rather than a
  local import because the caller is usually a *different process* than the broker.
- **`updates.py`** compares three numbers — **installed** (on disk), **running** (from
  the endpoint), and optionally **published** (the latest GitHub release).
- **The desktop app shows a banner when they disagree.** "Restart needed" (the broker is
  serving older code than what is installed) needs no opt-in — it only asks the local
  broker. "Update available" (GitHub has something newer) renders the release notes
  inline and is **strictly opt-in**: the app makes no external request unless the toggle
  is on, and the choice is persisted in `localStorage`.

### The version is single-sourced

`sys_buddy.__version__` now derives from the installed package metadata
(`importlib.metadata`) instead of a second hand-edited literal, so `pyproject.toml` is
the one place a version lives. `test_version.py` fails the build if the two ever drift.

### Docker packaging

A multi-stage root `Dockerfile` (built with `uv`) and a `docker-compose.yml` run the
broker as a single non-root container with a persisted `sys-buddy-data` volume for the
SQLite database. It defaults to **`serve`** (auth enforced) and never `local` — `local`
mode is unauthenticated by design and must not be reachable off-box. A `Makefile` wraps
the common flows and `.env.example` documents the tunnel setup for remote use.

### Automated releases

On push to `main`, release-please maintains an auto-versioned Release PR computed from
Conventional-Commit history, along with its changelog. Merging that PR cuts a GitHub
release and tag, and — in the same workflow, gated on `release_created` — publishes:

- **PyPI** via Trusted Publishing (OIDC, no stored secret): `uv build` → upload.
- **ghcr.io**, tagged with the version and `latest`, using the built-in token.

Publishing is chained *inside* the release workflow rather than triggered by the release
event, because a release created with `GITHUB_TOKEN` does not trigger separate workflows.

## Changed

### Tests became an actual merge gate

They were advisory — nothing ran them on a pull request, which is how the 1.1.0 startup
crash shipped.

- `ci.yml` runs `uv sync --frozen` + `uv run pytest -q` on every PR and on pushes to
  `main`, plus a guard job that fails any PR editing the `pyproject` version or
  `__version__` by hand. Releases own the version now; the guard skips release-please's
  own branch, whose entire job is to bump it.
- `pr-title.yml` enforces a Conventional-Commit PR title. The repo squash-merges, so the
  PR title *becomes* the commit release-please reads — keeping that input well-formed is
  what makes the automation trustworthy.

### Contributors no longer touch the version or the changelog

`CONTRIBUTING.md` now documents the conventional-commit PR title convention and the
type→bump table (`feat` → minor, `fix` → patch, `feat!` → major;
`docs`/`chore`/`refactor`/`test`/`ci` → no bump), and explains that one release bundles
every PR since the last and bumps once. `README.md` gained the matching install guidance
(tracking `main` vs. checking out a stable tag) and a versioning section describing the
automated flow.

### The always-listening design was revised in `v2.md`

Dogfooding showed the always-listening **subagent** re-injects its whole context on every
spawn — roughly 21k tokens *per message* — which is fatal for real, spread-out
collaboration. The design entry now has the main agent park on `wait_for_message` in its
own context (one load, cheap per message), with explicit turn-taking hints so agents
coordinate park-vs-yield without a human refereeing, and a give-up rule bounded by
`WAIT_CAP` that escalates rather than hanging. Documentation only in this release — the
prompt still told agents to spawn the subagent; that is fixed in 1.3.0.

The per-seat delivery invariant, the presence dot, and expiry-not-boolean all still
stand. Only the listener *mechanism* is superseded.

## Migration

- **None.** No schema change and no tool-surface change. Restart any long-running broker
  so `/api/version` exists and the process stops reporting stale code.
