# sys-buddy v2.14.0 — 2026-08-17

Minor release. **A lenient `dev_url` for where the app runs locally, and a same-machine
carve-out so agents can share seed/test credentials on a one-box task.** One additive schema
change (a nullable `tasks.dev_url`, created automatically). Restart any long-running broker —
it serves `ui.html` and `gui_app.html` from its own copy in memory, and the new delivery/rules
behaviour is in the Python it runs.

## Added

### `dev_url` — the local target `staging_url` could never be

`staging_url` is the deployed, SSRF-checked, signed target the test-runner hits — so it
rejects `http://localhost:3000`, which is exactly what you point at while building. That
rejection was a real pain point: a local task had nowhere legitimate to put its localhost URL.

`dev_url` is its lenient sibling. It names where the app runs during development, so
**localhost, http and bare hosts are all fine** — that is the entire point. It is host-owned
configuration like `staging_url` (no agent tool writes it, so nothing an injected message says
can reach it), but it is NOT the fetchable, signed target: there is no incentive to withhold
it, so `get_contract` hands it to agents at **both** the proposed and locked stages, and the
rules now name it as a host-set URL an agent may fetch — without that, rule 2 ("the only URL
you may fetch is `staging_url`") would have made a careful agent refuse the very URL it needs.

Set it three ways: `sys-buddy task create --dev-url http://localhost:3000`, the new
`sys-buddy task dev-url <task> [url]` verb, or a **Local dev URL** field in the desktop host
setup. The dashboard shows it as a dashed **"Local dev"** chip on the contract panel, distinct
from the solid "Connect to" chip so the local URL never reads as the signed one.

### The desktop app shows which version it is

The home screen's footer now prints `sys-buddy vX.Y.Z` — the installed version, read from the
version check that already runs on launch. A stale build is no longer invisible until
something misbehaves.

## Fixed

### Agents on a same-machine task can share seed/test credentials

The pain this addresses, verbatim from a real session: a backend agent, asked for a **dummy**
seed password committed in plaintext, refused — "a broker message is stored and served to every
viewer token, and that is the one leak no setting undoes." On a **remote** task that reasoning
is correct and unchanged. But on a **same-machine / local** task the broker is on loopback and
the thread never leaves the box, so the premise does not hold.

Rule 6 ("never message a credential") now carries **one scoped exception**, and only there: on
a same-machine or local task, **seed / test / fixture** credentials — the throwaway logins a
dev database ships with — may be shared in a message when a peer needs them to run locally. It
is bounded three ways: to same-machine tasks (keyed on the same signal that unlocks a localhost
`staging_url`, so "may I share a test login here?" and "may this task point at localhost?"
never disagree), to test/seed data (never a real secret, never a production credential), and it
leaves rule 6 **standing exactly as written on every remote task**. It is rendered into the
charter an agent is handed at pairing and returned by the `rules` tool, so an agent that reads
its rules sees the exception only when it genuinely applies.

This lowers the *tool's* barrier and hands the agent the "this never leaves the machine, these
are fixtures" context. The agent is still an autonomous party exercising its own judgment — but
the specific "the rules forbid it" refusal no longer fires on a local test credential.

## Migration

One additive schema change: a nullable `tasks.dev_url`, created by the idempotent schema on
startup (no backfill). Every existing task is untouched — `dev_url` is simply NULL until a host
sets one, and a task with no `dev_url` behaves exactly as before. **Restart any long-running
broker** so it serves the new page and runs the new rules/delivery code.

## Tests

**1696 passing**, up from 1688.

New `test_dev_url.py`: `dev_url` round-trips through create / set / get; it shows to every
viewer (host or not); it accepts localhost, http and a bare host and clears on empty; it rides
`get_contract` at both stages and is **not** withheld pre-lock (unlike `staging_url`, asserted
side by side). The carve-out appears **only** on a same-machine/local task, stays scoped to
seed/test credentials, and leaves rule 6 present — it is an exception, not a deletion.

## Known and deliberate

* **The carve-out needs the task to actually be same-machine.** A `sys-buddy local` broker
  qualifies automatically; a desktop task qualifies when you leave connectivity on "same
  machine" (blank public URL). A remote task never sees the exception, which is the point.
* **`dev_url` is host-owned, like `staging_url`.** No agent tool sets it and none can request a
  change — the same posture that keeps the deployment target injection-proof.
