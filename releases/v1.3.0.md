# sys-buddy v1.3.0 — 2026-07-26

Small minor release. One new status — **`waiting`** — that lets an agent nudge the
humans without declaring the collaboration dead, and one prompt fix that removes the
expensive background-listener recipe agents were still being told to follow. No schema
change, no tool-surface change, no migration.

---

## Added

### A soft `waiting` status — nudge the humans without marking stuck

The give-up rule could only escalate to `stuck`, which is **terminal**: it freezes the
whole collaboration. That is far too heavy for the common case — "the peer has gone
quiet and a human's attention would help."

`report_status("waiting", detail)` is a nudge. It pings Slack and drops a message plus
an event on the thread **without** changing state, touching strikes, or ending anything.
The task keeps its state and the agent can nudge again later.

- `STATUS_WAITING` / `_report_waiting` are handled *before* the mode gate, so it works on
  both contract and debug tasks.
- It is **task-level only**. A todo id is rejected, with a pointer to `stuck` with a todo
  for flagging one deliverable — a soft nudge about one deliverable is a message, not a
  status.
- It is refused on a terminal task, where there is nothing left to wait for.
- `waiting` joins the filterable event kinds in the API. The generic renderer already
  shows its text, so the dashboard thread and event log surface it with no further work.

This fills the last unbuilt piece of the v2 turn-taking design — the lightweight
`waiting` / `needs_attention` nudge that pings without marking stuck.

## Fixed

### Agents were still being told to spawn a listener subagent

Symptom — a per-message background listener that is ruinously expensive.

Cause — dogfooding measured a background listener reloading its whole context, roughly
**21k tokens on every spawn**. A loop that spawns one per message pays that repeatedly.
That finding was written into `v2.md` in 1.2.0, but the *prompts* still instructed agents
to do it, so the design change had no effect on live behaviour.

Fix — `STAY_LISTENING` (spawn a general-purpose subagent, never ack, respawn) is replaced
by `STAY_IN_THE_LOOP`: the agent parks on `wait_for_message` **in its own turn** and loops
— one context, and free while blocked — passes the floor explicitly when it sends, and
escalates a silent peer via `report_status` instead of parking forever. The matching
"background listener … never ack … check_messages" paragraph in the Rules of Engagement
was rewritten to the same wait-loop and give-up guidance.

### Floor-passing was vague prose, not a convention

The wait-loop guidance told agents to "say whether you're awaiting a reply" — too loose
for two agents to follow *consistently*, which is the only way a convention helps. It is
now a concrete end-of-message signal both sides read the same way:

```
"over to you"     → sender waits; receiver acts and answers
"I'll follow up"  → receiver waits; sender keeps the floor
"done for now"    → exchange at rest; receiver yields to its human
```

An unsignalled message means: act, reply, then wait once — do not assume more is coming.
The convention is in both the onboarding briefing and the rules charter, with a test
asserting all three signals are present.

## Migration

- **None.** The per-seat delivery invariant (`wait_for_message` = new,
  `check_messages` = unacked) is unchanged. Restart any long-running broker so agents
  receive the new briefings and `waiting` is accepted.
