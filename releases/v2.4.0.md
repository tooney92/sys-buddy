# sys-buddy v2.4.0 — 2026-08-04

Minor release, and a small one: **the app now tells you how to take the update it is
telling you about.** No schema change, no migration, nothing touched in the broker, the
auth path, the stream or the database.

---

## Added

### The update banner names the command, and it is the right one

v2.3.0 made the app check for new versions unconditionally. It would tell you a release
existed and show you what changed — and then stop, leaving you to already know how to
install it. Anybody who already knew did not need the banner.

It now shows the command, with a copy button. And it shows the **right** command, because
how you install determines how you upgrade:

| installed with | shown |
|---|---|
| `uv tool install` | `uv tool upgrade sys-buddy` |
| pipx | `pipx upgrade sys-buddy` |
| pip / a virtualenv | `pip install -U sys-buddy` |
| Docker | `docker pull ghcr.io/tooney92/sys-buddy` |

Detected rather than asked, from where the running interpreter actually lives —
a package manager decides that, so it is evidence rather than a guess. The **container
check runs first**, deliberately: the Docker image installs into a venv, so a
venv-shaped test would otherwise tell someone in a container to run pip at it.

Where nothing matches, it falls back to the `uv` command, since that is what the install
docs recommend. A wrong guess costs one wrong line of text to ignore — the banner shows a
string, never runs anything.

### "Restart needed" says what to actually do

It used to read *"restart the broker to apply the update"*, which explains the what and
not the how — and in a desktop app "quit and reopen" is not the obvious reading, because
quitting feels like giving up.

It now says: **Quit sys-buddy and open it again — the broker runs inside the app, so that
restarts it.** Plus one more sentence for the case that is otherwise a lie: if you started
a broker yourself in a terminal, the app **attaches to that one** rather than starting its
own, so quitting the app leaves it running and you have to restart the one you started.
No command block on this banner — the new code is already on disk, there is nothing to
install.

## Fixed

* `uv.lock` still pinned 2.2.0 while `pyproject.toml` said 2.3.0. release-please bumps the
  project version and not the lockfile, so every `uv run` dirtied the working tree with a
  diff nobody asked for. Relocked.
* Two comments still described the update-check opt-in that 2.3.0 deleted — a CSS marker
  for a checkbox that no longer exists, and a JS comment claiming the network call only
  happens "when it's on", sitting directly above the comment explaining that it is now
  unconditional. A comment that contradicts the code beneath it is worse than none.

## Migration

* **None.** No schema change, no table, no tool renamed or removed. One new field
  (`upgrade_command`) on the payload `/api`-adjacent version check already returned.
* **Restart any long-running broker** to pick it up — which the app will now tell you, and
  tell you how.

## Tests

**1428 passing**, up from 1419. Nine new: four install layouts parametrised (uv, pipx,
plain venv, and a Windows-shaped uv path), container-beats-venv, inconclusive-falls-back,
the field present in every payload including the offline one, the field surviving the
desktop bridge, and a source guard that the page renders it as **text** rather than markup.

Every layout is monkeypatched, including the container probe, so the tests cannot
accidentally pass because of how the machine running them happens to be installed — and
detection was then checked for real against the actual installed tool's interpreter, which
reports `uv`, the command a real user of the published package needs.

Driven in a browser across all three payloads: update-available renders notes, link and
command; restart-needed shows the new wording and no command row; up-to-date renders
nothing at all. The copy button was verified against a wiped clipboard using the Docker
string, which proves the page copies what Python sent rather than a hardcoded line — and
markup in the release notes rendered as literal text, confirming the `textContent` path
holds against remote content.
