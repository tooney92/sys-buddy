# sys-buddy v2.3.0 — 2026-08-04

Minor release. **The dashboard stops lying about being live**, engagement mode becomes
possible to create at all, and a todo opens over the board instead of replacing it.

**No migration steps.** Restart any long-running broker — and note that a broker started
before this release keeps serving its old code, which is now something the app tells you.

---

## Fixed

### Live updates could stop without the page admitting it

Watching a task through a tunnel, new messages never arrived — the page had to be refreshed
by hand. Locally the same version was fine, which is what made this confusing for a while.

**Measured against a real Cloudflare quick tunnel:** subscribed for 90 seconds, then again
for 45 with a message posted at +6 s. **Zero bytes, both times.** Not slow — nothing at all.
The HTTP response head only appeared when the client tore the connection down, and the
buffered body was discarded. `X-Accel-Buffering: no` is present on the loopback response and
**stripped** by Cloudflare.

Probing with a padded test stream put the threshold at roughly an edge buffer: 2, 8, 32, 48,
64 and 96 KB all produced nothing in 25 seconds; **128 KB flushed in 0.56 s**. So no
server-side change rescues SSE through a quick tunnel — the padding trick is written up as a
`DO NOT` in `_sse_ping` rather than shipped. **A named tunnel, ngrok or Tailscale all carry
it fine**; the quick tunnels do not.

That was the trigger. The defect was that the page could not tell:

* the stream sent **nothing at all** until the first real change, and the first keepalive
  was 15 seconds away, so through a proxy that buffers until it sees bytes the connection
  might never visibly establish;
* the keepalive was a bare `: ping` **comment**, and SSE comments are never surfaced to
  JavaScript — the liveness signal was on the wire and impossible to observe;
* `onerror` was unhandled, relying on the browser's own reconnect, which never fires for a
  connection that stays open and silent;
* **there was no fallback poll**, so the stream was not an optimisation, it was the only
  way data ever refreshed;
* and the "Live updates paused" banner only appeared on a *deliberate* pause, so a broken
  stream rendered as a healthy one.

So the stream is no longer something the dashboard depends on. It opens with a frame
**immediately** rather than after up to 15 seconds of silence — which on loopback moved
time-to-first-byte from **15.1 s to 0.02 s**, a real improvement quite apart from tunnels.
The keepalive is a named `event: ping` the client can actually observe, every 10 s. A
**watchdog** reopens a stream that has gone 45 s without a frame, and a **15 s fallback
poll** keeps the data fresh whatever the transport is doing. When it is degraded the banner
says so — *"Live updates unavailable — refreshing every 15s"* — instead of looking healthy.

`onopen` is deliberately **not** treated as liveness: through a quick tunnel it fires in
214 ms and then no data arrives for 30 s with `readyState` still OPEN. It only resets the
error counter.

Through a quick tunnel a message now lands in about 7 seconds with no manual refresh, with
the banner honestly showing degraded. On loopback it is effectively instant and the banner is
never created at all. A hidden tab still issues **zero** requests, so the pause gate holds.

### A dead dashboard link could not be replaced

The `sb_view` cookie outranked an explicit `?v=` token. It lives seven days, so a token
that stopped resolving — its database replaced, its viewer revoked — was re-sent and
re-rejected on every request, and a fresh link **could not override it**. The error screen
said *"ask your host for a fresh dashboard link"*; the resolver then refused to honour one.

Worst in the desktop app's dashboard window, which has no address bar, no devtools and no
private mode: there was no way out at all.

An explicit token now wins, a failed cookie is **cleared** rather than replayed for a week,
and the screen carries a **Try again** button that means something because of it. The
screen also stops claiming to know whether a token was invalid or revoked — it cannot tell.

One latent lockout went with it: `secure` was keyed on the configured public URL rather than
the request scheme, so any host with an https tunnel marked **every** cookie `Secure` —
including the one set when the dashboard is opened on `http://127.0.0.1:8787`, which is the
link `sys-buddy host-viewer` prints. Browsers silently refuse to send a Secure cookie over
http, so the page read "Access denied" with a perfectly valid token.

### Engagement mode had no door

Engagement mode shipped in **v2.1.0** — an owner seat, deliverables, guidelines per role,
owner-side verification, `confirmed`. Schema, domain layer, tools, dashboard and briefings
all supported it. **No user could create one.**

`admin.create_task` is the only path that makes a task, and it validated against
`("contract", "debug")` — so it raised on the one mode the release was named for. The CLI's
`--mode` offered the same two. So did the desktop app's radio group. Three surfaces spelling
the same list independently, and only the domain layer learned about the third.

One list now, read by all three, with tests asserting the CLI's choices and the app's radios
both match it — so a workflow added later cannot ship unselectable. The app also gains the
`owner` seat (offered only on an engagement) and `designer`, unreachable there since v2.0.0.
It refuses an engagement with no owner seat, and refuses the host taking that seat: the owner
is the client, and a host auditing themselves is the arrangement engagement mode exists to
prevent.

### An expired agent token was a dead end that lied about itself

A tunnelled broker gives agent tokens a 24h TTL so a leaked one self-expires, and the code
that does it says *"agents refresh with rotate_token"*. They cannot: `rotate_token`
authenticates with the token it would replace, so the moment one expires the agent loses the
only tool that could have saved it — and `report_status("stuck")` with it, so it cannot even
escalate. Nothing warned beforehand.

And the failure said *"invalid or revoked agent token"* for all three possible causes, which
for the commonest one is actively misleading: an agent told it may have been **revoked** sends
its human hunting a revocation nobody performed. The real answer was a clock.

**`sys-buddy task extend-tokens <task>`** is the host-side move that did not exist — with
`--hours`, or `--never` for a long session or a demo. Recovery previously meant revoking the
seat, minting a fresh invite, re-pairing, rewiring the MCP client and restarting the agent's
session, losing its context. It prints which seats were already dead, and says plainly that
nothing else is needed: the broker re-reads the token on every call, so the agent is live
again immediately. Only LIVE agents are touched — extending tokens must never quietly
re-admit somebody a host deliberately cut off.

The error now names which of the three it was, and for an expiry it names the command and who
runs it. Distinguishing them leaks almost nothing: an attacker holding no token still gets
"not recognised"; only somebody who once held a real one learns it expired, and that somebody
is the agent trying to work out why it stopped.

## Added

### A todo opens over the board, not instead of it

Selecting a todo used to swap the right-hand column in place, so you lost the list the
moment you wanted one item — no way to compare two, and a dedicated back button to return.
It opens as a modal now: status across the top, because the two state fields describe the
todo rather than either half of it; the human prose on the left, scope read in the open
rather than behind a toggle; the contract on the right. Click outside, press Escape, or use
the ✕.

Every piece is the same renderer the old column used, so this is a re-layout rather than a
second implementation.

### The app tells you when a new version exists

All the machinery was already there — a banner, release notes, a link. The check sat behind
a footer checkbox that defaulted to **off**, so it told nobody anything: four releases
shipped while this project's own author ran 1.4.0 and hit two bugs live that were already
fixed upstream.

A control you have to discover before the app will admit it is out of date is not a setting,
it is a way of never mentioning it. The check is unconditional now — one short request on
launch, silent when it fails, never blocking — and the banner links to the releases page on
the site rather than a raw tag, because that is the version written for somebody deciding
whether to upgrade.

The local half needs no network at all: **installed ≠ running** means you upgraded and the
old broker is still serving, which is the trap that once hid a schema migration.

## Migration

* **None.** No schema change, no table added, no tool renamed or removed. Verified by
  migrating a copy of a real 33-task database forward: every task readable, host and buddy,
  nothing raised.
* **Restart any long-running broker.** A process started before this release serves its old
  code, and its dashboard is the old `ui.html`.
* **Coming from 1.x, re-brief your agents.** Since v2.0.0 a contract belongs to a
  deliverable, so `propose_contract(spec, todo=N)` and `lock_contract(version, todo=N)` name
  it, and a `staging_url` inside a contract spec is refused — it is host configuration now.
  A new task briefs agents correctly for free; an in-flight one does not.

## Tests

**1419 passing**, up from 1390.

Beyond the unit tests, the parts that only fail in the real world were driven in the real
world: the stream measured through an actual Cloudflare quick tunnel before and after, the
dashboard driven in Playwright over that tunnel *and* on loopback in both themes, the cookie
lockout reproduced and then recovered in a browser profile that was genuinely stuck, an
expired token revived on a live broker, and an engagement created end to end past every gate.

One honest gap: the three auth messages could not be exercised over a full MCP round trip,
because MCP requires a session handshake before authentication runs. The reason-detection is
tested directly against a real database for all three cases instead, plus a test asserting the
helper is importable — it was not, and that would have raised `NameError` at request time
while every other test passed.
