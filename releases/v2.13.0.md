# sys-buddy v2.13.0 — 2026-08-16

Minor release. **The guest can now message one person or a few, everyone can get notified of
new activity, and `backend + guest` is a valid task.** One additive schema change (a new
`message_recipients` table, created automatically). Restart any long-running broker — it serves
`ui.html` and `gui_app.html` from its own copy in memory.

## Added

### A guest can direct a message at specific people

Her message box grew a **"To"** row of the other people on the task, as tick-boxes. They are
**people, not roles** — the seat, not the role type — so ticking "Tony" reaches `frontend-1`
and not the other frontend. That distinction is the whole point: addressing the tag `FE` fans
out to *every* frontend, and until now that was the only way to direct anything.

- Tick **nobody** → everyone on the task (the unchanged default).
- Tick **one** → private to that person.
- Tick **several** → just those few, nobody else.

The checked set lives in the page's state like the draft does, so a background refresh never
loses her picks mid-compose, and the thread renders one `→ Tony  → James` chip per recipient.

### One message can carry several directed recipients

This is the piece that made "Tony *and* James, no one else" possible. `post_message` takes a
`to_roles` list; it resolves and de-duplicates each addressee, then collapses onto the existing
paths: zero → broadcast, exactly one → an ordinary directed `to_role`, two or more → a new
`message_recipients` table, one row per canonical addressee, with a NULL `to_role`.

So a **true broadcast is a NULL `to_role` AND no recipient rows**, and delivery matches a reader
against both. It is **purely additive**: every message written before this release has no rows
in the new table and delivers byte-for-byte as it did. Agents keep their single `to_role`
parameter untouched; the list is exposed to the guest's box for now.

### Browser notifications — opt-in, for every dashboard viewer

A **bell** in the header turns them on (one click grants permission and un-mutes). It rides the
**same live stream the thread already uses** — no new endpoint, nothing stored on the broker, so
it can never leak who is watching a task. When new activity you did not write lands on the task
you are viewing:

- a **tab-title badge** — `(2) sys-buddy` — always, so a returning glance carries a count;
- a **desktop notification** and a **soft chime** — only when your tab is in the **background**,
  so there is no pop while you are already looking at it.

The chime is synthesised in the page (no audio file shipped), your own messages never notify
you, clicking the pop focuses the tab, and returning to the tab clears the badge.

## Fixed

### `backend + guest` is now a task you can create

The setup picker required **two builders**, a rule that predates the guest being able to sign
anything. Now that she is a full signing party, a contract needs **at least two parties and at
least one builder** — so `backend + guest` creates (James builds, she signs off), while
`backend` alone or `guest` alone still does not. The one-developer-plus-a-non-technical-partner
case — the exact reason the guest seat exists — no longer forces a throwaway second agent.

## Migration

One additive schema change: a new `message_recipients` table, created automatically by the
idempotent schema on startup (no backfill, nothing to run). Every existing message is untouched
and keeps delivering exactly as before. **Restart any long-running broker** so it serves the new
page and picks up the new delivery path.

## Tests

**1688 passing**, up from 1678.

New coverage: a message to `to_roles=[frontend, mobile]` reaches each and no one else; the
envelope lists all its targets; a single-element list collapses to a plain directed message; a
tag and its role de-duplicate; an empty list broadcasts; an unknown addressee is refused. On the
guest route: she directs a note to one person, to several, broadcasts when she ticks nobody, and
is 400'd for an addressee not on the task.

Proven live against a local broker: a guest message to `["backend","frontend"]` stored with a
NULL `to_role` and two `message_recipients` rows, the composer's "To" tick-boxes rendering the
real people, and the thread showing the `→ Bee  → Eff` chips.

## Known and deliberate

* **Notifications need a tab open.** They ride the browser's live stream, so they reach a viewer
  whose tab is open (background is fine) but not one whose browser is fully closed. Reaching her
  when it is shut (email / Slack) is a larger, separate change and deliberately not in here.
* **Multi-recipient is the guest's for now.** The `message_recipients` machinery is general, but
  only the guest's box exposes it; agents keep their single `to_role`, which already fans out to
  a whole role type when they want several.
